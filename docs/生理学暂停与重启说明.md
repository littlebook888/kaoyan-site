## 一、为什么暂停

两个目标都要（用户原话：「同步量下降是主要目标，还是渲染卡顿是主要目标？我觉得这两个都是目标」）：

| 目标 | 只隐藏 UI 能否达成 | 结论 |
|---|---|---|
| 降低云端同步量 | ❌ 同步量由 `tasks` 表**行数**决定，隐藏 UI 一行不少 | 必须**移出tasks 表** |
| 降低首屏渲染开销 | ✅ 不渲染即可 | 移出后自然达成 |

→ 采用「**移表**」方案：43 条生理学任务搬进轻量表 `rolling_reviews_paused`。

## 二、现在做了什么（代码层，已上线）

### 1. 卡片不再渲染任务，但机制完整保留

`tasks.js` 的 `renderPhysio()` 改为：

1. 先尝试走**完整渲染逻辑**（`renderRollingCard`）
   —— 若数据还在本机（未迁移 / 已回滚），卡片照常显示，**功能一点不丢**
2. 本机没数据 → 降级渲染「已暂停」说明块（含本文档路径）

>⚠️ 这点很重要：**暂停是"数据不在本机"造成的，不是"代码被删了"**。
> 所以任何时候把数据搬回来，界面立刻复原。

### 2. 通用渲染器（为两个系列共用）

`renderRollingCard(cfg)` / `bindRollingCard(cfg)` —— 逻辑自 physio 原实现
**原样搬迁**，只把固定值参数化（`elId` / `dataAttr` / `color` / `list` / `idx` …）。

新增系列只需写一个 `cfg` 工厂函数，不必复制整段交互代码。

### 3. 数据源没动

`static/js/xizong-physio.js`（`window.PHYSIO_PLAN`，DAY1-43）**完全保留**，
导入函数 `autoImportPhysioPlan()` 也保留 —— 重启时无需重新生成计划。

## 三、怎么重启（约 2026-11-08）

### 步骤 1：搬回数据

打开 `sql/生理学暂停迁移-20261008.sql`，执行**第 5 段**（被注释掉的 `insert into public.tasks ...`）。

```sql
insert into public.tasks
  (id, user_id, title, done, date, category, slot, block, subject, task_type,
   estimated_min, remind_on_estimate, total_focus_sec, status, time_record_ids,
   source, day_label, note, rr_note, created_at)
select p.id, p.user_id, p.title, p.done, '' as date, 'general', null, null,
       'xizong', 'review', null, true, p.total_focus_sec, 'todo', '{}',
       'physio_rolling', p.day_label, p.note, p.rr_note, now()
from public.rolling_reviews_paused p
where p.source = 'physio_rolling'          -- ★ v1.42.1 必须加：cleaned 后表里可能有其他系列
order by p.day_num;
```

> ⚠️ **原版漏了 `rr_note`**，v1.42.1 已补上。漏了它，这个月写在笔记框里的内容会丢。

### 步骤 2：★ 先清暂停标记（v1.42.1 新增，顺序不能颠倒）

```sql
-- 云端标记（跨设备）
update public.koujue_state set data = '{"v":""}'::jsonb, updated_at = now()
 where scope = 'physio_rolling_paused';
```

然后在**每台设备**的浏览器控制台执行：

```js
localStorage.removeItem('xizong_physio_paused');
localStorage.removeItem('xizong_physio_imported_v2');   // 保险：让守卫重新评估
```

> 🔴 **顺序很重要**：必须**先清标记、再搬数据**。
> 反过来做的话，`hydratePhysioPausedFlag()` 会把标记又写回去，暂停继续生效 → 卡片不出现。
>
> 💡 清完标记后前端会**自动**清localStorage（`hydratePhysioPausedFlag` 读到"未暂停"
> 就主动 `removeItem`），所以控制台那步其实只在离线时有意义。

### 步骤 3：刷新页面

数据一进 `tasks` 表，`renderPhysio()` 的第一步就会命中完整渲染 → 卡片自动恢复。

### 步骤 4（可选）：清理轻量表

确认恢复无误后再 `delete from public.rolling_reviews_paused where source = 'physio_rolling';`
（留着也不影响，只是不再更新）。

## 六、坑位记录（避免重启时重踩）

###① 「有调用、没定义」是按行号替换最易犯的错

本轮做「按行号批量替换」时，`bindRollingCard` 的**定义整段被覆盖掉，只剩调用**。
后果：页面能加载、语法检查全绿，但滚动复习卡片**所有点击交互整体失效**。

**对策（已落成断言）**：
```js
ok("★ v1.42.0 有调用必有定义（防按行号替换把函数体替换丢）",
  /function bindRollingCard\(cfg\)/.test(TK) && ...);
```
→ 凡是「有调用」的函数，必须同时存在「有定义」。

### ② 删除语句必须逐字复用插入语句的 WHERE

两个系列标题**都含"人可研梦滚动复习"**，只靠标题删会把新系列一起删掉。
SQL 里已用 `source='physio_rolling'` 作主判据 + `title not like '%内科%'` 兜底，
且两段 WHERE **逐字相同**。

### ③ RLS 缺 delete 策略会被静默拦截

`koujue_state` 上踩过：DELETE 返回 **HTTP 204（看似成功）但数据一行没少**。
本次建表时已直接写上 delete policy，并在注释里标注了这个坑。

### ④ 身份识别必须「认标题」，但**必须排除另一个系列**

`tasks` 表的 `source` / `day_label` / `note` 是**后补建列**，早期推送被"缺列自愈"
剥掉过、云端存成 `null`。**标题是唯一从未丢失的字段**，故 `isPhysioTask()`
双认 source 与标题。重启时若改回只看 source，老数据会全部识别失败。

🔴 **但两个系列的标题都含"人可研梦滚动复习"这7 个字**。v1.42.0 写的是
`PHYSIO_TITLE_RE = /人可研梦滚动复习/`，加上 source 是"或"关系 → **内科+病理的 44 行
也匹配** → 全部混进 `physioList()`，生理学卡会显示 87 个 DAY、进度算错、笔记挂错任务。
v1.42.1 已修：标题判据先排除 `isMedpathTitle()`，正则本身也收紧为必须含「生理学」。

### ⑤ 暂停后不加标记，`autoImportPhysioPlan` 会把数据**灌回来**

这是本轮最隐蔽的一个坑。守卫是：

```js
if (Store.getTasks().some(isPhysioTask)) return;   // "已有行→ 跳过"
```

暂停 = tasks 里**一行都没有** → 守卫判定为「**从未导入**」→ 立刻重新导入 43 行。
**暂停自我推翻，且每台新设备都会重灌一遍。**

v1.42.1 加了双层标记（`koujue_state` 的 `physio_rolling_paused` scope 跨设备+
localStorage 兜底防离线），并在 `autoImportPhysioPlan` 的**最前面**判定。

### ⑥ `on conflict (id) do nothing` 防不住「不同 id 的同一 DAY」

实测 `paused_rows = 129`（= 43 × 3）而 `tasks` 里只有干净的 43 行。
根因：历史上 `autoImportPhysioPlan` 在守卫失效时被跑过多次 → tasks 一度存在
**3 份不同 id 的同一 DAY** → `on conflict (id)` 只能挡住"同 id 重复插入"，
挡不住"三份不同 id" → 全被搬进paused 表。

v1.42.1 已改为**按 `day_num` 去重**（专注多的优先，其次 id 小的优先 —— 保证进度不丢），
并在第 3 段加了"每个 DAY 出现>1 次"的报警查询。
已发生的重复用 `sql/清理paused重复行-20261008.sql` 清理。
