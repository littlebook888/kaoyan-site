## 三、核心操作：粘贴这段 SQL 并运行

### 要粘贴的完整内容（原样复制，别改）

```sql
-- ============================================================
-- koujue_state —— 口诀复习站云同步（2026-10-07）
-- 用途：把「学习进度 + 自定义口诀 + 对内置口诀的修改 + 导入的口诀包」
--      整份存一份快照，按 scope 区分，手机/电脑/平板三端一致。
-- 为什么独立于 quiz_state（刷题站）：两边字段结构完全不同，共表会互相干扰。
-- 体积：实测约 17.5KB/份，每天整份上传月流量约 0.5MB，占 5GB 出网配额约 0.1%
-- 幂等：可重复执行，不会报错，也不会清空已有数据
-- ============================================================

-- ① 建表
create table if not exists public.koujue_state (
  scope      text primary key,          -- 固定是 'xk.v2'（对应浏览器里的存储键）
  data       text not null,             -- 口诀站整份状态的 JSON 快照（用 text 而非 jsonb，避免超长/特殊字符解析问题）
  updated_at timestamptz not null default now()   -- 谁新谁旧靠这个字段判断
);

-- ② 开启行级安全（默认所有外部访问都被挡住，下一步再精确放开）
alter table public.koujue_state enable row level security;

-- ③ 清掉可能存在的同名旧策略（幂等的关键）
drop policy if exists "koujue_state read"   on public.koujue_state;
drop policy if exists "koujue_state insert" on public.koujue_state;
drop policy if exists "koujue_state update" on public.koujue_state;

-- ④ 授权：允许 anon key 读 / 写
--    单人自用项目（无用户体系，表内只有你自己的数据），因此公开读写即可
create policy "koujue_state read"   on public.koujue_state for select using (true);
create policy "koujue_state insert" on public.koujue_state for insert with check (true);
create policy "koujue_state update" on public.koujue_state for update using (true) with check (true);
```

### 怎么粘贴

1. 点进 SQL 编辑器的大号输入框（等宽字体那个区域）
2. 直接 `Ctrl + V` 粘贴
3. **确认编辑器语言是 `SQL`**（右下角可切换，别选成 `PLpgSQL` 或 `JSON`）
4. 点右下角蓝色 **Run** 按钮（或按 `Ctrl + Enter`）

### 成功长什么样

执行成功后，下方 **Results** 面板会显示：

```
Success. No rows returned
```

或者

```
insert policy ...  (如果你勾了逐条执行，会看到若干行命令确认)
```

⚠️ 只要**没有红色报错块**，就算成功。`Success. No rows returned` 是正常的——这段 SQL 不查数据。

### 失败长什么样

如果下方出现红色区域，写着 `ERROR: ...`，对照本文第六节「常见报错速查」处理。

## 四、建完表后，30 秒自检

**仍然在 SQL Editor**，新建一个标签，粘贴下面这段检查语句，Run：

```sql
-- 自检 1：表是否存在、列是否齐全（应返回 1 行，4 列）
select table_name, column_name, data_type
from information_schema.columns
where table_schema = 'public' and table_name = 'koujue_state'
order by ordinal_position;

-- 自检 2：三条策略是否都在（应返回 3 行）
select policyname, cmd from pg_policies
where schemaname = 'public' and tablename = 'koujue_state'
order by policyname;

-- 自检 3：RLS 是否已开启（rowsecurity 应为 true）
select relname, relrowsecurity from pg_class
where relname = 'koujue_state';

-- 自检 4：当前有没有数据行（此时应该是 0 行，第一次打开副站后就会有 1 行）
select scope, length(data) as bytes, updated_at from public.koujue_state;
```

**判定标准**：

| 自检项 | 期望结果 | 不对怎么办 |
|---|---|---|
| 1 | 1 行 × 4 列（scope / data / updated_at） | 列少了 → SQL 没跑全，重贴一次 |
| 2 | 3 行（insert / read / update） | 少了 → 策略段没执行，重贴一次 |
| 3 | `true` | `false` → 第②段没跑到，重贴一次 |
| 4 | 0 行 | 正常，说明还没人用过 |

也可以顺手在左侧 **Table Editor** 里找到 `koujue_state` 看到表。

## 六、常见报错速查

| 报错关键字 | 含义 | 处理 |
|---|---|---|
| `syntax error at or near "..."` | SQL 粘贴被截断或格式乱了 | 全选清空，重新完整粘贴一次（尤其是中文注释部分） |
| `relation "koujue_state" already exists` | 表已存在 | **不是错误**，说明之前建过，继续往下跑即可 |
| `policy "..." already exists` | 策略重名 | 因为前面有 `drop policy if exists`，正常不会出这个；若出现，检查是不是漏了 `drop` 那三行 |
| `permission denied for table koujue_state` | RLS 挡住了 | 说明第③④段没执行，重贴完整 SQL |
| `PGRST205`（页面 JS 控制台里） | 表还是不存在 | SQL 没在**当前这个项目**里执行。检查 Project URL 是不是 `nkwwtlgpfvhzetjsssvj` |
| `42501` / `new row violates row-level security policy` | 策略缺失 | 同上，重贴 |
| `Failed to fetch`（浏览器 F12 Network 里） | 大概率是本机代理/网络拦截，与表无关 | 换个网络（如手机热点）打开副站测试；本地排查见第七节 |

|---|---|

> ⚠️ **一个已知的坑：DELETE 会被静默拦截。**
> 实测对 `koujue_state` 发 DELETE 返回 **HTTP 204（看似成功）**，但复查数据**仍然存在** ——
> RLS 无 delete 策略时，PostgREST 返回成功但实际影响 0 行。
> 这不影响正常使用（本站只做读 + upsert，从不删行），
> 但**将来若要清理测试行，必须先补 delete 策略**：
> ```sql
> create policy "koujue_state delete" on public.koujue_state for delete using (true);
> ```
> **通用教训：REST 接口返回 2xx 不等于操作生效，必须回读确认。**

## 七、几个你需要知道的「为什么」

### 1. 为什么单独建表，而不是复用刷题站的 `quiz_state`？
`quiz_state` 存的是「按学科分片的答案/收藏/笔记」，`koujue_state` 存的是「一整份 17KB 的 JSON 快照」。结构、粒度、更新频率完全不同，混在一张表里会让两边的读取逻辑互相干扰，且体积差两个数量级。**分开是最省事也最不容易出错的方案。**

### 2. 为什么 `data` 用 `text` 不用 `jsonb`？
前端是 `JSON.stringify(S)` 出来的字符串，直接整段塞进去，`text` 最省心、不会因为个别特殊字符导致插入失败。数据库层面不做查询，所以不需要 `jsonb` 的索引能力。

### 3. 为什么权限是「公开读写」这么松？
这个项目是**单人自用**：没有用户体系、没有注册登录，访问者只有你自己。RLS 的作用只是「确认没有意外路径能读写」，`anon` key 本来就是公开在前端代码里的（谁都能看到），所以这里放开 select/insert/update 与主站其他表的做法完全一致。

⚠️ 唯一要注意的：**别把这个 anon key 用在会存放他人隐私数据的表上**。目前项目里所有表都是这个策略，属于个人备考项目的既定约定。

### 4. 为什么不需要 `delete` 策略？
口诀站的同步只用「读 + upsert（插入或更新）」两种操作，从不删行。而 upsert 在 PostgREST 里是靠 `insert` + `update` 两个策略实现的，所以这三个就够。（刷题站的 `quiz_state` 需要 delete，是因为它有清理垃圾行的需求。）

### 5. 万一建错了怎么办？
```sql
drop table if exists public.koujue_state cascade;
```
一条命令清干净，重新贴建表 SQL 即可。**不会影响任何本地数据**——本地 `xk.v2` 是权威源，云端删了只是重来一次。
